# Bolt Migration App on Fiori + RAP — Scoping & Phase Plan

Status: **draft for team review — not approved, nothing built.**
Prepared 2026-11-18 from the Bolt Playbook §3 template. Values marked ☐ are not yet
confirmed; each has a working default in §7.

## 1. Requirement (verbatim)

> We will create the GitHub account and keep the instruction documents in a way how it is
> now for individual clients..
>
> In the RAP application we will source every possible information file and keep in client
> specifications folder..
>
> Our web application will be completely replaced with RAP and Fiori..
>
> We create dashboard where every controlling will be linked..
>
> We will source the smartform and display to clients in a retrieve tab and initiate the
> migration process directly on the same screen.
>
> The moment we do that all the legacy files should be automatically through ODATA APIs it
> should transfer into Github account where you pick that for complete migration process..
>
> In the Migration page in Fiori screen we will be having the same process like how we are
> currently processing in the webapplication.

**Business outcome:** a client starts a Smart Form → Adobe Form migration from inside their
own SAP system with one click, with no manual file export or upload. Our engineer windows
pick the ticket up from GitHub exactly as they do today.

**Primary users:**
- **Client operator:** retrieves forms, starts migrations, does the SAP steps, confirms or
  reports problems.
- **Client administrator:** sets up the GitHub connection and assigns roles.
- **Vernasoft engineer (Claude windows):** works the ticket. Unchanged, and never uses the
  app; it reads GitHub only.

### What changes and what stays

| Today (web app) | After (Fiori + RAP) |
|---|---|
| Operator runs `ZSF2AF_R_LEGACY_GRAB`, which downloads `.md` / `driver_*.txt` to a PC folder | The same extraction runs inside the app; nothing touches the PC |
| Operator downloads the Smart Form XML in SMARTFORMS (Utilities → Download) | The app exports the XML itself (to be proven, see Phase 0) |
| Operator uploads the files in Bolt Console, which creates the branch and status file | The app creates the branch, files and status file in GitHub directly |
| Bolt Console shows status, Confirm / Report a problem / Stop | The Fiori Migration page does the same, reading and writing the same status file |
| Node backend holds the GitHub token | An SM59 destination in the client's SAP holds a repo-scoped token |
| — | **Unchanged:** the status-file protocol and gate, branch naming, the engineer windows and their tools, and every SAP step in SFP / abapGit (create the empty form, Pull, Push, Activate, Preview) |

`src/`). It already reads TADIR, FUPARAREF, NAST, TNAPR, `SSF_FUNCTION_MODULE_NAME` and RTTI,

Only its output layer (`GUI_DOWNLOAD` to a PC folder) is unusable from Fiori or background
processing. Phase 1 moves its logic into a class that returns the files as strings.

## 4. Consumers & authorisation

- **Operator:** Retrieve tab, Migrate, Migration page actions (Confirm, Report a problem,
  Stop, Raise a concern).
- **Administrator:** additionally the connection screen and settings.
- **Engineer:** no SAP access; GitHub only.
- **Authorisation:** a custom authorisation object for the app (operator / administrator
  activity), enforced in the RAP behaviour. ☐ Should the app also respect S_DEVELOP display
  rights for reading program source?
- **Row-level filtering:** none at first; every operator sees every form in the system.
  ☐ Restrict by package?
- **Audit:** the GitHub token is shared, so every status entry the app writes records the SAP
  user and timestamp in the entry text.

## 5. Non-functional

| | Target |
|---|---|
| Volume | Hundreds of Smart Forms per system (the grab is designed for 500+); dozens of active migrations |
| Retrieve list | Paged; opens in seconds; no source scanning on open |
| Migrate | Background job; a single form completes in under a minute; a bulk selection shows per-form results |
| Status refresh | On open and on the Refresh button; no polling (same decision as the web app, 2026-10) |
| Atomic branch creation | The branch appears only when all its files and the status file exist (commit first, then create the branch reference) |
| No lost updates | Status writes send the file's version; GitHub rejects a stale write; the app re-reads and re-applies (same protection as the web app) |
| Security | Token in an SM59 destination, fine-grained, one repo, contents read/write only; never shown in the UI or written to logs |

| **1 — Thin slice: Retrieve + Migrate one form** | Operator selects one form and clicks Migrate; a real ticket appears that an engineer window can work | Form catalogue CDS + service; grab logic moved into a class; GitHub client class; Migrate action; migration record table | `queue.mjs list` shows the new branch as READY, with the same files and status file the web app creates, and a window completes the interface step from it |
| **2 — Migration page (web-app parity) + cutover** | Run a whole migration from Fiori | Status reader / parser; Confirm / Report a problem / Stop / Raise a concern / Upload reference file actions; status mirror table | A full migration (interface → Context → layout → sign-off) runs end to end with Fiori as the only client UI. | **3 — Client specifications folder** | Everything SAP can tell us about the client, in their repo, before the first form | Refresh action writing `client_spec/` | `client_spec/` holds system facts, the full form inventory with output types and drivers, all SmartStyles, the logo list and naming conventions; engineers read it at window start |

## 11. Applicable traps

From the Bolt Playbook Appendix A and this project's build log:

- **RAP naming:** `ZBP_` only for behaviour pools; table names with no `_` at character 2–3
  (`ZT_*` is invalid).
- **Ship the service binding** in the repo with `PUBLISHED=true`.
- **abapGit serialization:** copy the outer structure from a real serialized object of the same
  type; domain-backed custom data elements.
- **Grab-specific rules stay in force:** never trust FUPARAREF's `PARAMTYPE` for the DDIC kind
  (use RTTI); match TNAPR on the exact SFORM column; one failing form must not stop a bulk run.
- **Status-file protocol (rulebook §16):** keep every header field; append entries, never edit
  earlier ones; the app never sets or clears `CLAIMED_BY`.
- **Line endings:** the migration repo's `.gitattributes` forces LF on `.xdp`. The app must
  commit LF text, or engineer clones show phantom changes (the cause of the ZMM_PO_DEMO
  "no branch" incident).
- **Reconcile branch naming** (§7 #6) before Phase 1e.
