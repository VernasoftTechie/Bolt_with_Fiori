Smart Form Migration app: Fiori discussion points

Screen sketches and the questions we need answered before the build is scoped.

Brief. We are replacing our web application with a Fiori app on a RAP (OData V4) back end, running in the client's SAP system.

The back end does all the GitHub integration: it sends the legacy form files to GitHub and reads and writes each migration's status file. The Fiori side only calls our OData service.

Questions for the Fiori developer

1. Platform

  • Which SAP release and UI5 version is on the target system, and is the Fiori Launchpad set up there?
  • Is the system on-premise or on BTP, and how will the app be deployed (Business Application Studio, transport)?
  • Does that release support OData V4 with Fiori elements, or are we limited to V2?

2. App type

  • Do you recommend Fiori elements (List Report and Object Page) or a freestyle UI5 app for these screens?
  • Can one app hold the dashboard, the Retrieve tab and the Migration page, or should they be separate apps or tiles?

3. Screens

  • Dashboard: counts by status, each linking to its list, plus a "needs your action" list. Is an overview page or a custom page the better fit?
  • Retrieve tab: a list of the client's Smart Forms with search, filters and multi-select, and a "Migrate selected" button. The list may hold hundreds of forms.
  • Migration page: status, who it is waiting on, the action-needed box, and the full activity timeline.
  • Action buttons: "I've done this — confirm", "Report a problem" (free text), "Stop", and "Raise a concern" after completion.
  • Connection screen: a "Test connection" button and a clear connected / not connected indicator.

4. Specific UI questions

  • Formatted text: status entries are Markdown. What is the best way to render them, and is a timeline control suitable?
  • Background actions: "Migrate" runs as a background job. How should the screen show progress and the result per form?
  • Refresh: we want refresh on open plus a manual Refresh button, with no constant polling. Is that straightforward?
  • Attachments: can the user attach a screenshot when reporting a problem, and upload extra reference files when needed?
  • Notifications: can the Launchpad notify the user when a migration is waiting on them?
  • Launchpad tile: can the tile show a live count, such as "2 waiting on you"?

5. What you need from the back end

  • Entities: Smart Form, Migration, Status Entry and Connection. Do you need anything else?
  • Actions: Migrate, Confirm, Report Problem, Stop, Raise Concern, Test Connection and Refresh.
  • Annotations and side effects: who writes the UI annotations (the ABAP developer in CDS, or you), and what do you need so the screen updates after an action?

6. Access and delivery

  • Roles: we need at least two, a client operator and an administrator. How should buttons be hidden or disabled per role?
  • Languages and devices: is English and desktop-only acceptable, or is mobile or another language needed?
  • Effort and order: what is your estimate for these screens? Can the Retrieve tab plus Migrate be built first, as a thin working slice?
  • Mock data: what do you need from us to start before the back end is ready (a mock service, sample data)?
