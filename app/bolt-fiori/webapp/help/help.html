How Bolt works

Bolt moves your Smart Forms to Adobe Forms. It runs inside the SAP system that holds the Smart Forms, so nothing has to be downloaded or uploaded by hand.

The screen is split in two:

  • Left - the process, in its order: 1 Smart Forms (choose), 2 Drafts (committed, not on GitHub yet), 3 Migrations (on GitHub, followed live).
  • Right - Setup and Help: every prerequisite with its status, and this guide.

The flow of one form

  1. On 1 Smart Forms you tick the form and choose Next, then Commit. The form gets the next serial number.
  2. Bolt produces its legacy files in SAP - the legacy grab (<FORM>.md), the driver program sources, the Smart Form XML and every custom Smart Style it uses - and sends them to a new GitHub branch <prefix>-<form> together with the status file.
  3. If GitHub cannot be reached at that moment, the form is kept as a draft (tab 2 Drafts) and is sent later.
  4. The migration engineer picks the branch up, builds the Adobe Form and writes every step into the status file. You see it live on 3 Migrations.
  5. When the engineer needs you (for example to pull an object with abapGit and test it), the migration shows Waiting on: client. You do the step and answer on the migration page - I've done this - confirm, or report a problem, ask a question, request a change.
  6. At the end the status is Migration Completed. A concern can still be raised afterwards.

The header shows the client name. The LIVE indicator in the Setup panel is green when GitHub, the target repository and the AI provider are ready.

Filters

Which forms can be selected

  • Available forms (never migrated) - yes.
  • Stopped forms - yes: this starts a re-process run with a new serial number and a new branch <prefix>-<form>-r2, with freshly produced files. The stopped run is closed (replaced).
  • Forms in migration (including drafts) or completed - no. One form has one open migration at a time. Ticking one is refused with a short message; Select all skips them and says how many.

Next and Commit

Next (n) opens the confirmation with the selected forms. Commit creates the migrations and sends them one after the other; each line shows its own result. If GitHub is not ready (see the Setup panel), the button reads Save as drafts and the forms wait on 2 Drafts.

The spreadsheet button exports the list as it is filtered.

2 Drafts - committed, not on GitHub yet

A draft is a committed Smart Form whose initial load (legacy files + status file) has not reached GitHub yet. It already has its serial number and keeps it.

How a form becomes a draft

  • It was committed while GitHub was not connected, no target repository was set, or the token could not push.
  • The send failed - network, certificate (STRUST), proxy, GitHub refused, the form could not be exported. The reason is shown in the Last attempt column.

What you can do

  • Send to GitHub on a row, or Send all drafts: tries again, as often as needed, until the initial load is on GitHub. The draft then moves to 3 Migrations.
  • Discard (bin icon): the draft leaves the list and the form can be selected again. The record is kept (as stopped) for the history.
  • Click a row to open the draft's page; the same two buttons are there. Legacy documents and the communication panel appear on that page once the draft is on GitHub (the branch must exist first).

The background job ZABR_BOLT_SYNC also retries drafts every 15 minutes once GitHub is set up - up to Maximum send attempts (default 5) per draft, so a draft that keeps failing does not run forever. Sending by hand from this tab or from the draft's page has no limit: repeat it as often as needed after fixing the cause.

A migration page

Opens from any list and always shows the status file as it is on GitHub now. While the page stays open it reads it again every 2 minutes - but never while you are typing an answer, have files staged or an action is running, so nothing you are writing is lost. Refresh reads it at once.

Header

Form, serial number, branch (link to GitHub), status, package, driver programs, output types, committed (when, by whom), sent to GitHub, picked up, completed, number of files. A complexity line follows when known.

Migration status - talking to the engineer

  • The timeline shows the status file, newest entry first: the engineer's entries and yours.
  • Waiting on: client with the engineer's note: do what it says, then choose
    • I've done this - confirm (a note is optional) - the only thing that lets the engineer continue after a manual step;
    • Report a problem, Ask a question, Request a change - a note or a file is required.
  • Raise a concern - whenever nothing is waiting for you, also after completion.
  • Files: drag them onto the box or Choose files (images, PDF, Word, text, log, XML, Markdown; up to 25 MB each); remove any before sending. They are pushed to <branch>/concerns/<time>/ and named in your entry.
  • A confirmation appears for 8 seconds; an error stays in the panel with its reason.

Stop and resume

  • Stop this migration (with an optional reason) pauses all work; the engineer will not continue on this branch.
  • Resume migration continues exactly where it was.
  • Re-process instead: select the form again on 1 Smart Forms for a fresh run on a new branch.

Legacy documents

The reference files on the branch. Add files (drag and drop or choose) and mark files for removal, then Save changes. Added files are pushed to the branch; removed files only leave this list - the branch is not touched, because the engineer may be working from it.

Status history (in SAP)

Every event with time, user and the status after it: committed, sent, status changed, confirmed, problem, question, change, concern, stopped, resumed, documents added/removed, replaced. Kept in SAP for analysis; the messages themselves stay in the status file.

Files on the branch, AI summary

All files Bolt put on the branch. AI summary writes a plain-language summary of the form from its legacy grab (with the built-in provider: the list of its sections).

Before you start - prerequisites

SAP (Basis / security)

  • Outbound HTTPS (443) from every application server to api.github.com (and to the AI provider, if one is used).
  • STRUST: the root and intermediate certificates of api.github.com in the PSE of Advanced - SSL client identity (default SSL Client Anonymous), then SMICM - Exit Soft.
  • A proxy, if needed: SICF - Client - Proxy Settings.
  • Roles: S_SERVICE for the OData service group ZAB_UI_BOLT_O4 for all users; S_TABU_NAM on table ZABT_BOLT_SECRT for Basis only.
  • Jobs: ZABR_BOLT_SYNC every 15 minutes, ZABR_BOLT_DRIVER_INDEX daily. Run the driver index once after installation - until then the Setup panel shows Driver index not built and only NACE drivers are known (see Glossary - Driver index).

GitHub

  • The client's migration repository and a token with Contents: Read and write on it.

AI (optional)

  • The built-in provider is enough for migrations. A real provider needs its API key and outbound access.

Troubleshooting - messages and what to do

SAP does not trust https://api.github.com yet (SSSLERR_PEER_CERT_UNTRUSTED)

SAP's own certificate store (STRUST) has no certificate that vouches for GitHub's server certificate. A browser has these built in; SAP has not. Certificates added in SPROXY or in a browser do not count - only the PSE the app uses.

  1. Get the certificates. In a browser open https://api.github.com - padlock - Connection is secure - Certificate is valid - tab Details. The Certificate hierarchy shows three levels: the root (top), the intermediate (middle), *.github.com / api.github.com (bottom). Select the root - Export - save as Base64-encoded ASCII, single certificate (.cer/.crt). Repeat for the intermediate. The bottom one is not needed.
  2. STRUST - double-click the PSE the app uses: SSL client SSL Client Anonymous (unless Setup - Advanced - SSL client identity says otherwise; DFAULT = SSL client SSL Client Standard). If it has a red cross it does not exist yet: right-click - Create first.
  3. At the bottom, Import certificate (icon under the certificate area) - choose the root file - Add to Certificate List. Repeat for the intermediate. Then Save (Ctrl+S). Importing without Add to Certificate List and Save changes nothing.
  4. SMICM - Administration - ICM - Exit Soft - Global (all application servers), wait until the ICM is running again.
  5. Try Connect again. To test without the app: SM59 - new type G destination, host api.github.com, port 443, tab Logon & Security - SSL Active, certificate list ANONYM - Connection Test. Any HTTP answer (even 404) means SSL works; the same SSSLERR means the certificates are not yet in that PSE.

Still failing after this? Check that the import went into the PSE named in the message, that the ICM was restarted on every server, and ask Basis whether the system needs a proxy (then the error is usually a timeout instead).

The AI provider refused the API key (HTTP 401: invalid x-api-key)
The connection works (certificates are fine) - the provider does not accept the key. Usually the key was copied incompletely: an Anthropic key starts with sk-ant-api03- and is about 100 characters long; the console shows it only once, so create a new one if in doubt (console.anthropic.com - API keys - Create key). Also check that the key is not disabled and its workspace is active. An admin key (sk-ant-admin01-) cannot be used. HTTP 400 credit balance too low means the key is fine but the account needs credits; HTTP 404 on the model means the model name is wrong (e.g. claude-sonnet-5-5).
Connection refused / timeout
The system cannot reach the internet directly - set the proxy (SICF - Client - Proxy Settings) or an SM59 destination under Advanced.
That token wasn't accepted by GitHub
Wrong, expired or incomplete token - create a new one and connect again.
... the token cannot push / read-only
Give the token Contents: Read and write on the repository (or add the GitHub user as collaborator with write access).
Couldn't find "owner/name"
Typo in the repository, or the token cannot see it.
Saved as drafts / Draft - sending failed
Fix the cause shown (usually one of the above), then Send to GitHub on 2 Drafts.
Nothing is waiting for your confirmation right now
The engineer is not waiting for you - use Raise a concern to write to them.
This migration is stopped. Resume it first.
Resume, then answer.
Another user is committing a selection right now
Try again in a moment (serial numbers are given one commit at a time).
... is already in migration / already migrated - skipped
That form has an open or completed migration; open it from the Migration column.
Add your own user ID ... to the administrators
The administrators list must contain the user who saves it.
Only Bolt administrators can change the configuration
Ask an administrator, or to be added to the list.
The system information / the Bolt setup could not be read from SAP

What is stored where

All tables are cross-client: one set per system, whichever client the app is opened in.

ZABT_BOLT_SETUP
The Setup page (one row, DEFAULT).
ZABT_BOLT_SECRT
GitHub token and AI key - encoded, never sent to the screen.
ZABT_BOLT_MIG
One row per migration: serial and run number, branch, sent state, and the status read from the status file (status, waiting on, stop, picked up by, last status update, time of the last read), picked up / stopped / completed dates, complexity, files count. Updated at every read from GitHub.
ZABT_BOLT_HIST
One row per event and per status change found at a read (date, user, status, waiting on, stop) - the status history; no message texts.
ZABT_BOLT_FILE
The files on each branch.
ZABT_BOLT_LIB
The global reference library list.
ZABT_BOLT_DRVIX
The driver program index.

The messages between you and the engineer are not copied into SAP: they stay in the status file on the branch (docs/legacy_grab/<form>_status.md), the one place both sides read.

Glossary

Branch
The migration's own line of work in the GitHub repository, <prefix>-<form> (-r2, -r3 for re-process runs).
Status file
The file on the branch where the engineer and you record every step; Bolt shows it as the timeline.
Driver index

A Smart Form never prints on its own: a driver program reads the data and calls it. The engineer needs that program's source to rebuild the same logic for the Adobe Form, so it goes to GitHub with the legacy grab.

Some drivers are easy to find: output-type printing is configured in NACE (table TNAPR names the program). Many are not - custom reports, function modules and enhancements that call the form directly through SSF_FUNCTION_MODULE_NAME, with no output type. The only way to find those is to read the source of every custom program and look for the form name next to that call (within 20 lines).

Reading every custom program takes minutes, far too long for the Smart Forms list or a commit. Report ZABR_BOLT_DRIVER_INDEX does it once in the background and stores the result (table ZABT_BOLT_DRVIX: form - program). The app then only looks the form up.

Without it, nothing breaks: the list and the legacy grab show NACE drivers only, so a form printed by a custom report shows no driver and the engineer gets no driver source for it. Run it once now (SE38, background is fine - prefixes default to the Setup page), then daily as job Z_AB_DA_BOLT_DRIVER_INDEX so new programs are found. The Setup card turns green once it has run.

Legacy grab
The automatic description of the Smart Form (interface, windows, texts, conditions, driver programs, output types) the engineer builds from.
Draft
A committed form whose initial load is not on GitHub yet.
Re-process run
A fresh migration of a stopped form, on a new branch.
Engineer window
The migration engineer's working session; shown as Picked up by.
